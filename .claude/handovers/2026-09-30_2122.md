## 決定事項

- **ホスト UI は Flutter（add-to-app 相当の埋め込み）+ ネイティブのコアで統一する**（ユーザ判断。WebView2 の方がメモリとアクセシビリティで有利という実測を踏まえたうえでの決定）
- Flutter エンジンは**常駐させる**（ウィンドウを閉じても破棄しない）
  - 閉じたら破棄しても 23MB しか戻らず、作り直すとかえって膨らむため、実測でも常駐が妥当
- UI ⇄ コアの通信は **Pigeon の `@HostApi` + `@FlutterApi` に全 OS で揃える**。EventChannel は使わない（Pigeon のイベントチャネルは Swift / Kotlin 専用で、C++ にはない）
  - macOS スパイクの EventChannel + JSON はこれに合わせて直す
- ネイティブコードを持つ Flutter プラグインは使わない。QR は `qr_flutter`、コピーは標準の `Clipboard`、外部を開く処理は Pigeon 経由でネイティブに任せる
- トレイ / メニューバーのアイコンとメニューはネイティブのまま残す
- UI スレッドは STA にし、`CoIncrementMTAUsage()` で暗黙の MTA を残す
  - libwebrtc のスレッドが COM を初期化しないまま MF / WinRT を呼んでいるため（`media_foundation_h264_encoder.cpp:135`、`session_controller.cpp:147` の resize）
- 文言は `tools/i18n` の Dart 出力（`dart.mjs`）で生成する。ネイティブ側に残る文言（トレイメニューなど）は既存の出力を使う

## 捨てた選択肢と理由

- **WebView2 / システム WebView（Web UI）**: ユーザ判断で不採用。実測では次の点で優位だった
  - 閉じたら破棄すると 42MB まで戻る
  - UIA でボタン・URL が見え、UIA 経由で承認して配信できた
  - 配布物の増分は +42KB
  - ビューアのツールチェーンをそのまま使える

  不利だった点は次のとおり
  - 開いている間は +154MB（6 プロセス）で、Flutter より重い
  - 休止（TrySuspend / LOW）はほぼ効かない（−6MB）
  - 維持者は Flutter の方が流暢
- **Qt Quick / QML**
  - 本体は `/MT`、Qt の DLL は `/MD` で、C++ の API をまたいで CRT が混在する
  - iOS での LGPLv3 の扱いが要確認
  - Swift から使う手段が弱い（Qt Bridge はプレビュー段階）
  - 維持者が QML に不慣れ
- **Slint**: Swift / Kotlin のバインディングがない。モバイルは Rust のみ。既存ウィンドウへの埋め込みは自作になる。アクセシビリティの状況が不明確。About への帰属表示義務がある
- **Compose Multiplatform**: デスクトップが JVM 前提。ネイティブ版は非公式フォークのみ
- **.NET MAUI / Avalonia**: .NET のホスト、または .NET ランタイムの同居が必要
- **React Native（RNW / RN-macOS / brownfield）**: ツールチェーンが 3 系統とも最も重い
- **wxWidgets**: iOS / Android に対応していない
- **Dear ImGui**: アクセシビリティがない
- **Tauri**: アプリ全体を所有する構造で、既存プロセスに埋め込めない
- **Sciter / Ultralight**: OSS ではない
- **GPUI / gpui-mobile**
  - GPUI は `Application::run()` でアプリを所有する作り。`HasWindowHandle` は「GPUI の中に他のものを入れる」向きで、既存の HWND / NSView には入れられない
  - gpui-mobile 0.1.0（2026-09-15、コミュニティ製）は慣性スクロールの部品だけで、本体は未公開の upstream crate 待ち
  - アクセシビリティがない（AccessKit は予定止まり）
  - Rust 専用
- **Lynx（ByteDance）**: 埋め込み専用で構造は合うが、デスクトップ対応が 2026-04 と新しく、アクセシビリティとメモリの情報がない。様子を見る扱い
- **Flutter エンジンを閉じるたびに破棄する**: 上記「決定事項」のとおり、効果が小さく逆効果もあるため不採用

## ハマりどころ

- **パスが長いと vcpkg が失敗する**: scratchpad（長いパス）の worktree では、boost のヘッダ展開が MAX_PATH を超えて `boost-config` のビルドに失敗した（エラー 3）。worktree は `C:\Work\OpenSource\` の直下など、短いパスに置く
- **Ｃドライブの空き不足**: 途中で空きが 79MB になり、Flutter エンジンの展開が止まった（ユーザが確保して 33GB）。Flutter の成果物 + worktree 側の vcpkg + ビルドで 4〜5GB を見込む
- `flutter build windows --config-only --release` は、PATH に cmake がないと最後に「Unable to generate build files」で失敗する。ただし `generated_config.cmake` は出力されるので実害はない。client wrapper と DLL は、ビルド時に `flutter_assemble` が用意する
- Pigeon の `headerIncludePath: 'generated/host_api.g.h'` は、`/` をそのままインクルードガード名に入れてしまう。`'host_api.g.h'` だけにして、同じディレクトリから引かせる
- Flutter の CMake は `cmake_minimum_required(3.14)` で CMP0091 が未設定になる。ただし結果的に wrapper も `MultiThreaded`（`/MT`）になり、LNK2038 は出なかった
- `flutter_windows.dll` は C の ABI なので、CRT の違いは問題にならない
- 生成された Dart に `for (final x of ...)` を書いてしまった（Dart の正しい構文は `in`）。`dart.mjs` で修正済み
- Windows PowerShell 5 は、BOM なし UTF-8 の `.ps1` を ANSI として読む。日本語のコメントが化けて改行を巻き込み、`param(...)` が消えた。計測用スクリプトのコメントは英語にする
- PowerShell から `FindWindow(class, $null)` と呼ぶと、`$null` が空文字列として渡る。`[NullString]::Value` を使う
- `SetForegroundWindow` は前面化の制限で効かないことがある。Alt キーを送ってから呼ぶ
- **Flutter の UIA には `FLUTTERVIEW` の枠しか出ない**（待って取り直しても同じ）。WebView2 は 2 回目の問い合わせで Document / Button / Edit まで出た
- スパイクで二つのビルドを同時に走らせたら、`.d.json` への書き込みが Permission denied になった。単独でビルドし直したら通った
- 計測で撮影スクリプトが `ShowWindow` を直接呼んでいたため、アプリの `show()`（作り直し）を通っていなかった。再表示は `WM_COMMAND 200`（トレイの「ウィンドウを表示」）で行う
- 前回からの持ち越し: `apps/web/package-lock.json` と `package.json` の不整合。今回の CMake ビルドでは `npm ci` が通っていたが、原因は確認していない

## 学び

- Windows 版 Flutter のアイドル時メモリは、このマシンで Private 141MB（素の runner）。macOS（+34MB）の 4 倍近い
- Flutter の Dart VM と DLL は、エンジンを破棄してもプロセスから抜けない。「閉じたら解放」はできない
- WebView2 はコントローラを `Close()` すると子プロセスごと終わり、ホスト単体の 42MB に戻る。休止系の API はほとんど効かない
- Flutter の Windows 埋め込みは add-to-app として公式にはサポートされていない（調査による。3.47 の文書が対象とするのは Android / iOS / macOS / Web）。ただし公開されている C++ の client wrapper（`FlutterViewController`）と生成 CMake だけで組み込めた
- `SessionController` の Snapshot + change handler（`PostMessage`）という既存の分け方が、そのまま UI ブリッジの境界になった。コア側の変更は不要だった
- 状態の push は 1 秒ごと（トークンのカウントダウン用）+ 変化時で足りる
