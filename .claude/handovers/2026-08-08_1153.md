## 決定事項

- **構成**: ホスト（ネイティブアプリ）／ビューア（ブラウザのみ、専用アプリなし）／ランデブー（シグナリング専用）の 3 要素
- **シグナリングのみクラウド経由、映像・入力は P2P**。同一 LAN では ICE が LAN 候補を選ぶため実トラフィックは外に出ない
- **プラットフォームごとにネイティブ実装**。共有するのは「ワイヤプロトコル」と「Web ビューア」のみ
- **WebRTC は Google libwebrtc を全プラットフォームで採用**。ビルド済みバイナリを使い自前ビルドはしない
- **コーデックは v1 で H.264**（全プラットフォーム HW エンコード + Safari 対応）。AV1 は両端対応時のみネゴシエーションで選択
- **座標は 0.0–1.0 の正規化値**で送る。解像度変更・ズーム・レターボックスから独立させる
- **DataChannel は 2 本**: `control`（reliable/ordered）と `pointer`（maxRetransmits:0 / unordered）。クリック・キーは自身の絶対座標を持つため順序非保証でも成立する
- **キーは `KeyboardEvent.code`（物理キー位置）で送る**。IME 変換結果はキーイベントから復元できないため `text` メッセージを別に持つ
- **ビューアは必ず閲覧のみで接続開始**。ホスト側の明示トグルなしに入力は一切通さない（`SessionController` で遮断）
- **ランデブーサーバは信頼しない**。SDP / ICE をペアリングコード由来の鍵で AEAD 暗号化してから渡す
- **iOS ホストは閲覧専用**（非脱獄 iOS に入力注入手段が存在しないため）
- **macOS は Mac App Store 非対応**。Developer ID 直配布 + notarization
- ビューアは v1 でフレームワークなし（TypeScript のみ）。状態管理が破綻した時点で Svelte を検討し ADR に残す
- マイルストーンは M0（macOS→ブラウザで映像が出る、閲覧のみ）から M7 まで定義済み。各段階で「動く製品」を維持する

## 捨てた選択肢と理由

- **Rust 共有コア（webrtc-rs）**: トランスポートは書けるが帯域推定が未成熟。画面配信の品質を決める輻輳制御を自作することになる。また iOS の Broadcast Extension / Android の MediaProjection は結局ネイティブ実装が必要で、共有できる範囲が想定より狭い
- **FFI（UniFFI 等）による共有コア**: 共通化できるのは signaling / セッション / 入力デコードで計 1000 行程度。4 プラットフォーム分の FFI ビルドチェーン維持コストに見合わない
- **SPAKE2 等の PAKE によるペアリング**: 40bit のワンタイムコード + TTL 3 分 + レート制限で必要強度を満たせるため、実装・監査コストに見合わない
- **ホスト自身が Web ページを HTTPS 配信する LAN 直結モード（v1 での採用）**: 自己署名証明書の警告か、実証明書の同梱・更新運用が必要になる。クラウドの HTTPS ページ + P2P メディアなら証明書問題自体が発生しないため v1 では不要と判断（将来のオフラインモードとしては残す）
- **カーソルの別チャネル送出（v1）**: `showsCursor = true` の焼き込みで足りる。プロトコルに `cursor` メッセージだけ予約して実装は先送り

## 学び

- `.claude/CLAUDE.md` が `@../SPEC.md` を import しているため、SPEC.md は毎セッション全文がコンテキストに載る。肥大化させないよう構造を保つ必要がある
- iOS の ReplayKit Broadcast Upload Extension はメモリ上限が約 50MB。PeerConnection を Extension 内に持つ必要があり、フレームのコピーを増やす実装は即クラッシュする
- Android は一般アプリによる任意の入力注入を許さない。`AccessibilityService.dispatchGesture()` ではタップ・長押し・スワイプ・システムナビゲーションまでで、任意のキー入力は不可。よって「右クリック」は Android ホストに存在せず、プロトコルを意味論的イベントにしてホスト側でマップする必要がある
- Windows は UIPI により自プロセスより高い整合性レベルのウィンドウに入力を注入できない。UAC プロンプト・ログオン画面の操作には SYSTEM サービス + セッションエージェントの二段構成が要る
