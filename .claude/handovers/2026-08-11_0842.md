## 決定事項

### 画面ごとに URL を分ける（SPEC.md §11-3、ユーザ承認済み）

```
http://192.168.1.10:8422/?d=1#<token>   ← 内蔵ディスプレイ
http://192.168.1.10:8422/?d=4#<token>   ← 外部ディスプレイ
```

- `DisplayStream` が画面 1 枚ぶんの `ScreenCapturer` + `VideoPipeline` + `PeerTransport` を持つ。
  `SessionController` は権限・一覧・待受・振り分けだけを見る god object をやめた
- **`RTCPeerConnectionFactory` は 1 つを共有する。** 画面ごとに作ると VideoToolbox の
  セッションも人数分増える。分けるのはトラック ID（`screen-<displayID>`）だけ
- **指定された画面が無いときに黙って別の画面へフォールバックしない。** 意図しない画面を
  配信するほうが有害なので、理由を返して切る
- 波及: SPEC.md §1.2 の「1 対多配信」は「同じ画面を複数のビューアへ」に書き換え。
  §1.3 の接続形態は「1 画面 : 1 ビューア」。トークンは**接続確立で失効させない**
  （失効させると 2 画面目を繋げなくなる。無人アクセスを防ぐのはトークンではなく承認）

### 承認するまでキャプチャを開始しない（SPEC.md §5.2）

待受を始めた時点では何も撮っていない。ビューアが来ると `.awaitingApproval` になり、
ホストが承認して初めて `SCStream` が動く。**承認前に画面の内容が符号化されることがない**、
という形で無人アクセス不可を保証する。ビューアが去ったらキャプチャも止める。

これに伴い「開始」ボタンの意味が変わった（キャプチャ開始 → 待受開始）。
プレビューは「実際に配信しているもの」しか映さないので、承認前は空になる。理由を重ねて出す。

### 解像度追従（SPEC.md §7.1）

- ビューアは表示領域を**物理ピクセル**で申告する（`innerWidth × devicePixelRatio`）。
  CSS ピクセルで送ると高 DPI 端末が実解像度の半分しか受け取れない
- ホストは 720p / 1080p / 1440p / 2160p の**直近上位**へ丸める（`VideoEncoding.followingSize`）。
  実解像度にぴったり合わせるとリサイズのたびにエンコーダ再構成とキーフレームが走る
- 当て方は **`SCStream.updateConfiguration`**。張り直すと毎回数フレーム落ちてキーフレームからやり直し

## 捨てた選択肢と理由

- **全画面を 1 枚に連結して送る**: 解像度が跳ね上がり、遅延の支配要因（エンコード）を
  自分で悪化させる。§11-3 で明示的に不採用
- **承認を検証モードで迂回する**: `--serve` は「承認待ちを見つけたら `approve()` を押す」
  ループを回すだけで、**製品と同じ承認経路を通る**。裏口を作ると検証しているのが製品でなくなる
- **プレビュー用に選択中の画面を常時キャプチャする**: 「承認前は撮らない」という保証が崩れる。
  プレビューが空なのは「本当に何も送っていない」ことの表示として正しい
- **品質プリセット（SPEC.md §7.2）を今回入れる**: 制御チャネルの器はできたが、
  使わない列挙子を先に置かない。必要になった時に足す

**ずれても動く**（設計どおり）が、ログの読み違いのもとになる。`lsof -nP -iTCP:8422 -sTCP:LISTEN` で見る。

## 学び

- **「1:1」の意味を取り違えない。** SPEC.md の「1 ホスト : 1 ビューア」は
  「1 画面 : 1 ビューア」の意味だった。画面ごとに独立させても simulcast / SFU は要らず、
  非目標（§1.2）とも衝突しない。制約の**理由**まで戻ると、変えてよい所が見える
- **承認をプロトコルではなく「キャプチャを開始する条件」に落とすと保証が強くなる。**
  「承認されるまで送らない」より「承認されるまで撮らない」のほうが検証しやすく、破りにくい
- **バジェットの支配要因を潰すと、次の支配要因が顔を出す。** エンコード 17.4 → 7.8ms の
  代わりにジッタバッファが 8.3 → 15.4ms に見えるようになった。合計はまだ 33ms
