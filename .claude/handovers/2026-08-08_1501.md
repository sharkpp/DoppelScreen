## 決定事項

- **`LocalServer` は HTTP（既定 :8422）と HTTPS（既定 :8423）を同時に待ち受ける。** 同一ハンドラを両リスナで共有し扱いに差を設けない。ポート使用中は空きポートへずらし、実際のポートを QR / URL に反映する
- **QR / URL の既定は HTTP**（証明書警告が出ないため）。HTTPS の QR / URL もホスト UI に併記する
- **ビューアページはロード直後に WebRTC 可否を自己診断する。** `typeof RTCPeerConnection === "undefined"` の場合、または PeerConnection は生成できたが 5 秒以内に接続が確立しない場合、HTTPS 側 URL への切り替えをワンタップで案内する。トークンは URL fragment のまま引き継ぐ
- **自己署名証明書の要件を確定:**
  - 初回起動時に生成し**永続化する**（毎回生成すると受け入れ済みの証明書例外が毎回無効になり警告が繰り返される）
  - **SAN にホストの IP アドレスを含める**（URL が IP ベースなので CN だけでは Safari / Chrome とも受け付けない）。IP 変更時は再生成
  - **HSTS ヘッダを送らない**（送ると当該ホストへの HTTP アクセスが恒久的にブロックされ HTTP 経路が死ぬ）
- **ビューアの WebSocket スキームは `location.protocol` から導出する**（`https:` → `wss:`）。HTTPS ページから `ws:` は混在コンテンツでブロックされる
- **Screen Wake Lock API はセキュアコンテキスト限定のため HTTP 経路では使えない。** モニタ用途では必須級の機能なので、この場合は HTTPS 経路への切り替えを案内する
- **HTTP / HTTPS の別は映像・制御の暗号強度に影響しない**（DTLS-SRTP / DTLS-SCTP は WebRTC 標準で無効化不可）。HTTP 経路で平文になるのはビューアページと SDP のみで、いずれも LAN 内に閉じる
- **両待受と証明書の永続化は M0 に含める。** 後から足すと証明書の同一性設計をやり直すことになるため
- §11-1 は設計上のブロッカーではなくなり、「QR の既定を HTTP のままにしてよいか」という**既定値の調整**に格下げ。実機で HTTP がほとんど使えないと分かった場合のみ既定を HTTPS に入れ替える（自己診断による誘導が毎回走るのは体験として悪いため）

## 捨てた選択肢と理由

- **HTTP 単独**: Screen Wake Lock などセキュアコンテキスト限定 API が使えず、ブラウザが `RTCPeerConnection` にセキュアコンテキストを要求する環境で成立しない
- **HTTPS 単独**: 端末ごとに初回の証明書警告通過が必要で、QR を読んだらすぐ映るという体験を損なう
- **M0 での実機検証を待って一方に決める（前案）**: 両対応にしたことで検証がブロッカーではなくなった。実測は既定値の調整材料として使う
- **公的 CA の証明書（`*.lan.sharkpp.net` のワイルドカード DNS を RFC1918 に向ける Plex 方式）**: 接続時に DNS 解決のためインターネットが必要になり、「クラウド・インターネット非依存」という本設計の中核と矛盾する。証明書配布・更新の運用も発生する

## 学び

- 「HTTP か HTTPS か」を二択と捉えていたのが誤りだった。両方を同時に待ち受けるのはリスナが 1 つ増えるだけでコストがほぼ変わらず、実機検証待ちのブロッカーを設計から消せる
- 自己署名証明書は「生成できること」より**同一性を保てること**が要件。再生成すると証明書例外が無効化され、ユーザーは毎回警告を見る。だから M0 から永続化を入れる必要がある
- HSTS は「とりあえず付ける」がセキュリティ上の定石だが、HTTP 経路を残す設計では**付けてはいけない**。ブラウザ側に恒久的な状態が残り、後から取り消せない
