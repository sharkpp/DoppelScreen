## 今回やったこと

- **「システムで許可済みなのに『許可を求める』ボタンが無反応」という報告を調査し、原因を特定して修正**
- 原因は 2 つの複合。いずれも macOS の TCC 仕様
- 権限まわりの UI と API 呼び出しを作り直し、`make macos-reset-permission` を追加
- `docs/STACK.md` §2.5 に「画面収録権限の落とし穴」を追記
- TCC 記録をリセットしてアプリを再起動済み（次はプロンプトが出る状態）

## 決定事項

### 原因（調査結果）

1. **`CGRequestScreenCaptureAccess()` がプロンプトを出せるのはアプリごとに一度きり。** 二度目以降は何も起きず false を返すだけ。UI は状態が変わらないので「無反応」に見える
2. **開発ビルドは ad-hoc 署名（署名 ID が 1 つも無い環境）。TCC は署名でアプリの同一性を判定するため、cdhash がビルドごとに変わる開発ビルドは、リビルドすると別アプリ扱いになって許可が失われる。** システム設定のリストには残ったまま実際には拒否されるので原因が分かりにくい
   - `security find-identity -v -p codesigning` → **0 valid identities found** を確認済み
   - `codesign -dv` → `flags=0x2(adhoc)` / `TeamIdentifier=not set` を確認済み
3. （付随）システム設定で許可しても、実行中のプロセスには反映されない。**再起動が必要**

### 修正内容

- `ScreenRecordingPermission` に `hasRequestedBefore`（`UserDefaults` に記録）を追加。**一度尋ねたあとはプロンプトが出ないことを前提に導線を切り替える**
- `ScreenRecordingPermission.relaunch()` を追加（`NSWorkspace.openApplication` + `createsNewApplicationInstance` → 完了後に `NSApp.terminate`）
- `SessionController.requestPermission()`: `request()` が false を返したら**そのままシステム設定を開く**。押して何も起きない状態を作らない
- `OnboardingView`: 初回は「許可を求める」、二度目以降は「システム設定を開く」＋「再起動して反映」に切り替え。**ad-hoc 署名で許可が外れる件の説明文も出す**
- `MainView`: 未許可の間は **1 秒ごとに権限をポーリング**して追従（`.task(id: session.permissionGranted)`）
- `Makefile` に `macos-reset-permission`（`tccutil reset ScreenCapture` + `defaults delete`）を追加

### 恒久対策の方針

**Apple Development 証明書（開発者アカウント）を用意した時点で `project.yml` の `CODE_SIGN_IDENTITY` を ad-hoc から切り替える。** 安定した署名 ID なら Designated Requirement が Team ID + Bundle ID ベースになり、リビルドしても許可が維持される。それまでは `make macos-reset-permission` で回す。

## 捨てた選択肢と理由

- **自己署名証明書をキーチェーンに作って署名する**: ad-hoc より安定するが、ユーザーのキーチェーンを変更する作業であり、開発者アカウントを用意すれば解決する話。回避策として恒久化させる価値がない
- **`CGPreflightScreenCaptureAccess()` の代わりに `SCShareableContent` を毎回叩いて実権限を判定する**: より正確だが、ポーリングで叩くとプロンプトを繰り返し誘発しうる。ポーリングは軽い preflight で行う
- **「許可を求める」ボタンを常に出す**: 二度目以降は機能しないため、出し続けると同じ混乱を再生産する

## ハマりどころ

- **`CGRequestScreenCaptureAccess()` の戻り値は「許可されたか」であって「プロンプトを出せたか」ではない。** 拒否済みと「既に尋ねた」を公開 API で区別できないため、`UserDefaults` で自前に記録するしかない
- **システム設定のチェックが入っていても、cdhash が変わっていれば拒否される。** 「設定上は許可済み」という見た目が診断を難しくする。`tccutil reset` で一度消すのが確実
- **`tccutil reset ScreenCapture <bundle-id>` は自分のアプリなら特権なしで実行できる。** TCC.db の直接読み取りはフルディスクアクセスが要り、`authorization denied` になる

## 学び

- **TCC の同一性判定は「Bundle ID」ではなく「署名」。** ad-hoc 署名で開発する限り、リビルドのたびに許可が外れるのは仕様どおりの挙動であり、バグではない。開発ループに `tccutil reset` を組み込むのが正解
- **「押しても何も起きない」を作らないことがオンボーディング設計の要件。** API が黙って false を返す場合、UI 側で必ず次の手（システム設定を開く／再起動する）に繋ぐ
- 権限状態は外部（システム設定）でいつでも変わる。イベント通知がないためポーリングが要る。`didBecomeActive` だけでは、設定アプリを開いたまま許可した場合に追従できない
