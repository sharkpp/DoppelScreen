## 決定事項

### ドキュメント構成

- `SPEC.md` は `.claude/CLAUDE.md` から毎セッション全文が読み込まれるため、実装レベルの詳細を入れると肥大化する。スタック情報は `docs/STACK.md` に分離した

### Web ビューア

- **Vite + TypeScript + `vite-plugin-singlefile`。フレームワークなし**
- 単一 HTML への落とし込みが効く理由: ホスト側が「1 ファイルを返すだけ」になり、静的配信のルーティング・MIME 判定・キャッシュ制御がすべて不要になる。**ホスト実装が 4 プラットフォーム分あるので効果が 4 倍になる**
- テストは Vitest。プロトコルのエンコード／デコードと解像度追従を純粋関数として切り出す

### macOS ホスト（M0 の主戦場）

- デプロイメントターゲット **macOS 14+**。依存はすべて SPM（CocoaPods / Carthage は使わない）
- WebRTC: `stasel/WebRTC`（SPM でビルド済み xcframework、iOS と共用）
- HTTP + WebSocket: **SwiftNIO**（`NIOHTTP1` + `NIOWebSocket`）。HTTP と WS アップグレードを 1 ポートで捌ける
- TLS: `NIOTransportServices`（`NIOTSListenerBootstrap`）で Network.framework 経由のシステム TLS を使う。BoringSSL を抱え込まない
- 証明書生成: `apple/swift-certificates` + `apple/swift-crypto`。秘密鍵・証明書は Keychain に保存（Application Support に平文で置かない）。SAN には `getifaddrs` で列挙した全 LAN IP を入れる
- QR: Core Image `CIQRCodeGenerator`（依存追加なし）
- **キャプチャ→WebRTC は `RTCCVPixelBuffer` でラップするだけでコピーしない**。`SCFrameStatus == .complete` 以外は破棄
- `SCStreamConfiguration.queueDepth` は 3–5。大きすぎるとフレームが溜まって遅延になる
- `minimumFrameInterval` は**上限 fps の指定**であって下限ではない。SCK は変化時に配るので待たされない

### M0 の実装順（層を積み上げる）

1. Xcode プロジェクト + SPM 依存
2. 画面収録権限のオンボーディング（権限なしで黙って動かない UI を先に作る）
3. **SCStream で自己プレビュー** — ネットワークを触る前にキャプチャを確定させる
4. **libwebrtc をループバックで検証** — 同一プロセス内に PeerConnection を 2 つ作って直結。シグナリングもブラウザも介さないので切り分けが容易
5. HTTP サーバ（:8422）で単一 HTML を返す
6. WebSocket シグナリング（`/signal`）→ ここで初めて end-to-end が通る
7. HTTPS リスナ + 証明書生成（:8423）
8. 遅延計測オーバーレイ

### 他プラットフォーム

- Windows: C++/WinRT + CMake + vcpkg、Boost.Beast（HTTP/WS/TLS 一式）、UI は WinUI 3。**Media Foundation の H.264 HW エンコーダを `webrtc::VideoEncoderFactory` として自前登録が必要**（libwebrtc の Windows ビルドは標準でソフトウェアエンコーダのみ）。4 プラットフォーム中もっとも手間がかかる箇所
- Android: Kotlin + Ktor Server(CIO)。`ScreenCapturerAndroid` に `MediaProjection` を渡すだけで済み、Ktor が証明書生成から HTTPS・WebSocket まで一式そろう。**4 プラットフォーム中もっとも実装量が少ない**
- iOS: macOS とコード共有。**M5 の最初のタスクは機能実装ではなく「libwebrtc + NIO + H.264 エンコードが 50MB に収まるか」の検証**。収まらなければ NIO をやめて `NWListener` + 手書き最小 HTTP/WS に置き換える

## 捨てた選択肢と理由

- **Windows ホストを C#/.NET で実装**: WinRT 射影で `Windows.Graphics.Capture` は扱えるが libwebrtc をネイティブに使えない。純 C# の WebRTC 実装（SIPSorcery 等）は帯域推定が未成熟で、webrtc-rs を却下したのと同じ理由で不適
- **Hummingbird / Vapor（macOS の HTTP サーバ）**: ルーティングが必要な規模ではない（返すのは単一 HTML と `/signal` の 2 分岐のみ）。SwiftNIO を直接使う
- **Network.framework の `NWListener` 単体（macOS）**: `NWProtocolWebSocket` を有効にすると全接続が WebSocket になり、プレーン HTTP と同一ポートで共存できない。ポートを分けるか RFC 6455 のフレーミングを手書きすることになる。NIO なら 1 ポートで両方扱える（ただし iOS でメモリが足りない場合はこちらに退避する）
- **NIOSSL（BoringSSL）**: Apple プラットフォームでは `NIOTransportServices` 経由でシステム TLS が使えるため、BoringSSL をバイナリに抱え込む理由がない
- **CocoaPods / Carthage**: SPM で全依存がまかなえる

## 学び

- **B フレーム無効化は自前実装が不要な可能性が高い。** libwebrtc の VideoToolbox H.264 エンコーダは内部で `kVTCompressionPropertyKey_RealTime = true` と `AllowFrameReordering = false` を設定していると見られる。SPEC.md §3.2 のレバーだが、**独自エンコーダを書く前にまず実測する**（`docs/STACK.md` §7-4 に要確認事項として記載）
- ビューアを単一 HTML にする判断は、ビューア側の都合ではなく**ホスト側の実装量を 4 プラットフォーム分削るため**の判断。効果の出どころが逆側にある
- ステップ 4（libwebrtc のループバック検証）を挟むのが重要。キャプチャ・エンコード・デコードの問題と、シグナリング・ネットワークの問題を分離できる
