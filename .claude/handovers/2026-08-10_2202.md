## 決定事項

### エンコーダファクトリを自前にする

libwebrtc 既定の `RTCDefaultVideoEncoderFactory` を捨て、`H264EncoderFactory` を置いた。

- **level 5.2 を広告する。** 既定は level 3.1 を広告し、VideoToolbox は level の制限を
  実際に強制するため 1080p 以上で 1 枚も出力しない
- **ネゴシエートされた level を無視して符号化する。** level は answer で下げられる
  （Chrome も libwebrtc も 3.1 を返す）。`level-asymmetry-allowed=1` があり、
  復号側が見るのは SDP ではなくビットストリーム中の SPS
- **H.264 以外を広告しない。** 失敗が静かなコーデック切り替えに化けないようにする
- level 5.2 を超える解像度（5K 以上）は `VideoEncoding.encodableSize` で縮小してから渡す

### 解像度は落とさない（M1 では）

エンコード時間を削るには解像度を下げるのが確実だが、**画質の方針は M2 の解像度追従
（SPEC.md §7.1）で決めるべき**と判断し、M1 では level 5.2 の上限だけを見て
ディスプレイの実解像度のままにした。**M2 の解像度追従がそのまま最大の遅延削減策になる。**

### 配線

- 映像は `addTransceiver(direction: .sendOnly)` で張る。転送専用（SPEC.md §1.2）を
  SDP に明記し、送出できないコーデックがネゴシエートされる余地も消す
- 送出パラメータ（ビットレート・`degradationPreference`）は**ローカル記述を入れた後**に当てる。
  それより前は送出側のパラメータが確定していない
- `--serve` の `--duration` は「合計の実行時間」。接続の 3 秒後に切っていたため、
  手で繋ぐと画面が出た直後に切れていた

## 捨てた選択肢と理由

- **`RTCDefaultVideoEncoderFactory.preferredCodec` で High Profile を先頭にする**:
  既定の並びで既に `640c1f`（Constrained High）が先頭なので**何も変わらない**。
  問題は profile ではなく level だった
- **level をビューアの answer に合わせる**: Chrome も libwebrtc も 3.1 を返すため、
  合わせると必ず壊れる。`level-asymmetry-allowed` があるので合わせる必要がない
- **answer の SDP を書き換えて level を上げる**: 同じ結果を `createEncoder` の中だけで
  得られる。SDP マンギングは持ち込まない
- **エンコード解像度を 1080p 級に丸める（M1 で）**: 遅延には効くが、文字の可読性という
  製品の核を M1 の都合で削ることになる。M2 の解像度追従で表示先に合わせる方が正しい
- **WebCodecs 描画経路（SPEC.md §8.3）**: 表示以外の合計が約 36ms で、`<video>` の
  合成を差し引いても目標内。**進まなくてよいと判断できた**

## ハマりどころ

### 【重大】H.264 のつもりで VP8 が流れる

- VideoToolbox は level の**最大フレームサイズと最大ビットレート**を実際に強制する。
  実測（上限 40Mbps）: 1920×1080 は level 4.0 以上、2880×1800 は level 5.0 以上が要る
- 超えると `encode` が最初のフレームで -1 を返し、以後 1 枚も出力しない
- **libwebrtc はこの失敗をコーデックの切り替えで隠す。** `framesEncoded` は伸び、映像も出る。
  実際に流れているのは VP8 のソフトウェア符号化で、ビューア側もハードウェアデコードできない
- 見分け方: `encoderImplementation` の統計（`VideoToolbox` 以外なら落ちている）。
  ループバックでは `decoded.png` が `RTCI420Buffer` で書き出せなくなる

### コーデックの統計は `codecId` から引く

`codec` の統計は**ネゴシエートされた全コーデックぶん**現れる。種別だけで拾うと
使っていないものを掴む（実際に H.264 なのに VP8 と報告された）。M0 の実測記録が
誤っていた原因の半分はこれ。`RTCStatisticsReport.mimeType(of:)` を用意した。

### HTTPS が「繋がるのに応答しない」

- キーチェーンの確認ダイアログが未応答のまま残っていると、TLS ハンドシェイクでの
  秘密鍵の使用が止まる。`ERR_TIMED_OUT` / `ERR_CONNECTION_REFUSED` になる
- **証明書の取得（`SecIdentity`）は通るので `certificateError` は `nil` のまま。**
  ログからは分からない。`pgrep SecurityAgent` で残っていないか見る。「常に許可」を一度押す

### `RTCVideoTrack` に `contentHint` は無い

obj-c API は `addRenderer` / `removeRenderer` しか持たない。品質プリセット（M2）は
`RTCRtpEncodingParameters` と `degradationPreference` で表現する。

## 学び

- **「映っている」は「意図した経路で映っている」ではない。** コーデックもエンコーダ実装も
  統計で名指しして確認する。libwebrtc は失敗を隠して動き続けるので、
  **静かなフォールバックを持たせない**（H.264 以外を広告しない）方が診断しやすい
- **ライブラリの既定値を疑うときは、ライブラリを直接叩いて切り分ける。** 今回は
  `RTCVideoEncoderH264` を単体で叩き、level × 解像度の表を作ったことで原因が確定した
  （`scratchpad` に使い捨ての Swift を書いて `swiftc -F` で xcframework にリンクした）
- **バジェットは配分ではなく「どこが支配的か」を見るために使う。** 内訳を出した結果、
  M1 の残りの仕事が「M2 の解像度追従」だと分かった
