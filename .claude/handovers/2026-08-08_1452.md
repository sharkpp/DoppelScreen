## 決定事項

### スコープ（ユーザー回答により確定）

- 1:1 のみ
- 音声・クリップボード同期・ファイル転送は**なし**
- 無人アクセス**不可**。ただし QR による接続サポートは持つ
- **入力転送（クリック / キーボード / スクロール / IME）は完全に非対象**。「後から足せるように」ではなく設計から除去する
- 主にローカルネット想定。帯域コストの考慮は不要
- 切断時のホスト画面ロックは不要（ユーザーが操作している画面を映す前提）
- ミラーリングであり、拡張ディスプレイ化は非目標

### アーキテクチャ

- **クラウドを一切使わない。ホストアプリ自身がビューアの Web ページを配信し、シグナリングも自分で受ける**（`LocalServer` = HTTP + WebSocket）
- ランデブーサービス・STUN・TURN・SDP の E2E 暗号化はすべて**不要になったので削除**。ICE は host candidate だけで成立する
- WebRTC / libwebrtc ビルド済みバイナリ採用は前案から継続
- コーデックは H.264（iPad Safari でのハードウェアデコードが決定的）。LAN では帯域が制約にならないのでビットレートを潤沢に与えて量子化を浅くする
- DataChannel は `control` 1 本のみ（reliable/ordered）。メタ情報専用で、高頻度イベントがないためチャネル分割は不要
- **ビューア主導の解像度追従**: ビューアが `viewport`（表示先の物理ピクセル数）を送り、ホストがそれに合わせてキャプチャ・エンコード解像度を決める。500ms デバウンス + 段階値に丸める

### 遅延設計（本ソフトの中核）

- 目標: glass-to-glass **60ms 以下**（有線 LAN / 1080p60）。遅延バジェットを区間ごとに数値化して `SPEC.md` §3.1 に記載
- レバーの効果順: (1) `RTCRtpReceiver.jitterBufferTarget = 0` が最も効く、(2) B フレーム無効 + realtime エンコード、(3) 変化駆動エンコード、(4) 長 GOP + PLI（定期 I フレームの帯域スパイクを避ける）、(5) 表示経路の短縮
- **計測を M0 から作る**。getStats + `requestVideoFrameCallback` のオーバーレイに加え、カメラ同時撮影による glass-to-glass 実測手順を定義

### 更新差分の配信について（ユーザーからの問いへの回答）

- **独自の差分配信プロトコルは作らない。** H.264 のインター予測が skip マクロブロックで既に「変わった所だけ」を送っている。重ねても帯域も遅延も改善しない
- **効くのは「変化した瞬間に符号化を始めること」**。固定フレームレートだと変化から次のキャプチャ時刻までの待ち（60fps で最大 16ms、30fps で 33ms）が遅延に乗る。SCK / WGC / VirtualDisplay はいずれも変化駆動でフレームを配るので、それを即エンコードに回す。**採用**
- dirty rects は「静止時の送出停止」にのみ使う（遅延ではなく CPU / 電力 / 発熱に効く）。ROI エンコードは M0–M2 では採用しない

### 入力転送の除去による副次的効果（重要）

- macOS: **アクセシビリティ権限が不要になった**（必要な権限は画面収録のみ）
- Android: **`AccessibilityService` が不要になり、Google Play のアクセシビリティ API ポリシー問題が完全に消滅**（前案の最大リスクだった）
- Windows: UIPI / 整合性レベルの制約が消滅。SYSTEM サービス化も不要
- iOS: 「閲覧専用」という機能差が消滅し、**全プラットフォームが機能的に対等**になった

## 捨てた選択肢と理由

- **クラウドのランデブーサービス（前案の中心）**: LAN 限定・1:1・無人アクセス不可が確定した結果、存在理由がなくなった。ホスト直結なら中間者が存在せず SDP の E2E 暗号化も不要
- **WebSocket + WebCodecs（H.264 を TCP 送出 → `VideoDecoder` → canvas）**: ジッタバッファが存在せず理論上は最も低遅延で実装も単純。しかし TCP の head-of-line blocking により Wi-Fi でロスした瞬間に映像が固まる。LAN でも Wi-Fi は日常的にロスするため不採用
- **独自の差分配信プロトコル**: 上記の通りコーデックが既にやっている
- **ROI エンコード（変化領域にビットを寄せる）**: VideoToolbox / Media Foundation で安定制御できる保証がない。実測で必要と分かるまで着手しない
- **HEVC / AV1 のスクリーンコンテンツ符号化ツール**: 帯域効率は優位だが、LAN では帯域が制約にならないため遅延と互換性を犠牲にする価値がない
- **Rust 共有コア（webrtc-rs）**: 前案から継続で不採用（帯域推定が未成熟、キャプチャは結局ネイティブ）
- **カーソルの別チャネル送出**: 操作しないミラーリングなので、`showsCursor = true` の焼き込みで十分
- **Windows の SYSTEM サービス化**: 入力注入が不要になり、UAC / ログオン画面を映せないことの実害が小さくなった
- **永続的な信頼済みデバイス登録**: 無人アクセス不可なので不要

## 学び

- スコープ縮小が「単に機能を消す」以上の効果を持つ好例だった。入力転送を落としただけで、macOS の TCC 権限が 2 つ→1 つ、Android の Play ポリシーリスクが消滅、Windows の SYSTEM サービス化が不要化、iOS の機能差が解消、クラウド基盤が丸ごと不要化と、4 プラットフォームすべての最難関が同時に消えた
- 「差分配信で遅延が改善するか」は直感に反して No。ビデオコーデックのインター予測が既に差分符号化であり、遅延に効くのは差分ではなく**キャプチャの起動タイミング**（固定レート待ちの除去）
