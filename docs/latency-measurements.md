# glass-to-glass 実測

SPEC.md §3.3 の実測手順と、その記録。**リリースごとに同条件で測って、この表に足す。**

内訳（エンコード・ジッタバッファ・デコード）は `make e2e` が自動で測る（docs/STACK.md §2.11）。
こちらは**表示までを含めた実際の遅延**。**人の手が要るのは撮影だけで、読み取りは自動**
（`make latency-analyze`）。

---

## 1. 何を測るか

ホスト画面が変化してから、ビューア端末の画面にそれが出るまで。**目標は 60ms 以下**
（有線 LAN、1080p60 — SPEC.md §1.3）。

`make latency-clock` が出すカウンタをホストの全画面に表示し、**ホストとビューアを 1 台の
カメラで同時に高速度撮影する。** 同じコマに写った 2 つのカウンタの差がそのまま遅延になる。

```
   ┌─ ホストの画面 ──┐   ┌─ ビューア端末 ──┐
   │  ▛▀▙ ▟▀▛ ▜▀▛    │   │  ▛▀▙ ▟▀▜ ▙▀▛    │   QR: 123456 と 123406 → 50ms
   │      4821       │   │      4772       │   数字: 4821 − 4772 = 49ms
   │  ▁▁▁█▁▁▁▁▁▁▁▁   │   │  ▁█▁▁▁▁▁▁▁▁▁▁   │   ブロック差 3 × 16.7 ≒ 50ms
   └─────────────────┘   └─────────────────┘
```

読み取り手段が 3 つ重なっている。**上から順に自動化に向く。**

| | 読む人 | 内容 |
| --- | --- | --- |
| **QR** | `make latency-analyze` | 経過ミリ秒（1000 秒周期）。位置も取れるので**どちらの画面かを指定する必要がない** — 時刻が新しい方が必ずホスト |
| **数字** | 人 | QR と同じ時刻の下 4 桁。QR が読めなかったときの逃げ道 |
| **ブロック** | 人 | 1 個 = 表示 1 フレーム。**桁がブレて読めないコマでも位置の差は残る** |

**基本は自動（§3）。** 人が数コマ読むのに対して、解析は数百コマの中央値を採る。
自動が使えないとき（QR が小さすぎる、ピントが来ていない等）だけ手で読む（§4）。

## 2. 準備

| | 内容 |
| --- | --- |
| ホスト | `make macos-run` で起動 → 「配信を開始」。**ディスプレイのリフレッシュレートを確認**（省電力で落ちていると測っても意味がない。カウンタ下段の実測値を見る） |
| ビューア | 画面ごとの URL を実端末で開き、ホスト側で**承認**する。ビューアは**フルスクリーン**にする（映像をタップ） |
| ネットワーク | 有線が基準。Wi-Fi でも測るなら別の行として記録する |
| 送出解像度 | ホスト UI の「◯◯ へ配信中」の右に出る実効値をそのまま記録する。解像度追従（SPEC.md §7.1）でビューア端末ごとに変わるので、**条件として必ず控える** |
| カメラ | **240fps** 推奨（iPhone のスローモーション。設定 → カメラ → スローモーション → 1080p/240fps）。60fps だと 1 コマ 16.7ms で、目標 60ms に対して分解能が足りない。**書き出し方は問わない** — スローモーションのまま渡しても実際のレートを算出する（§3） |

**カウンタは毎フレーム全体が描き替わる。** 静止画を映して測ると、静止時の送出停止（SPEC.md §4.3）が
効いて何も流れず、遅延ではなく「止まっていること」を測ることになる。

## 3. 手順（自動）

1. ホストで `make latency-clock` → 開いたページを**全画面**にする（ブラウザの全画面表示）
2. ホストの画面とビューア端末を**並べて置く**。カメラから見て**両方が正面**になるようにする
   （斜めから撮ると液晶の視野角で沈んで読めない）
3. 1 台のカメラで**両方が同時に画面内に入る**ように 240fps で 10 秒ほど撮る
4. 動画を Mac に取り込み、解析する

```
make latency-analyze VIDEO=~/Desktop/IMG_0001.MOV
```

実際の出力（2026-08-11、Pixel のスローモーションで撮影）:

```
動画: PXL_20260811_142055586.mp4
  1920x1080 / 483.3s / コンテナ 30.0fps（表示上）

撮影レート: 239.8fps（1 コマ 4.2ms） ← QR の時刻から算出
  ※ スローモーション: コンテナは 30.0fps だが、実際は 240fps で撮られている
     （コマは間引かれていないので測定に影響しない）

遅延の中央値: 67ms   （目標 60ms 以下 — SPEC.md §1.3）
  最小 49ms / 最大 500ms / p10 50ms / p90 116ms
  読めたコマ 9481 / 14483 (65%)
```

各コマから QR を**すべて**読み、時刻の差を取って中央値を採る。**どちらの画面かを
指定する必要はない** — ホストは必ずビューアより新しいので、時刻の大小で決まる。

**撮影レートはコンテナの申告を信じない。** iPhone のスローモーションは 240fps で撮った
コマを 30fps 再生の尺で書き出すため、`avg_frame_rate` は 30 になる。QR に載っている
ホストの時刻を基準時計として使い、**コマがどれだけ実時間を刻んでいるかを測る**ので、
どちらの書き出し方でも実際のレートが出る。コマは間引かれていないので、尺が伸びていても
遅延そのものは変わらない。

スローモーションの検出は**実機（Pixel の `.mp4`）で確認済み** — コンテナ 29.96fps に対して
撮影 239.8fps（8.0 倍）と正しく出た。書き出し方を気にせず渡してよい。

- **読めないコマが出るのは正常。** 表示の書き替えとカメラの露光は同期していないので、
  一部のコマは 2 枚のフレームをまたいだ QR になって復号できない。実測で 65%。
  **0 コマなら QR が小さすぎるか、ピント・明るさの問題**（解析が候補を出す）
- **最大値が `--max-latency`（既定 500ms）に張り付いたら、上限で切られている。**
  裾を正しく見るには上限を上げて測り直す
- 記録用の JSON も残せる: `ANALYZE_ARGS="--json docs/latency/latency-<日付>-<版>.json"`
- コマ数を間引きたいときは `ANALYZE_ARGS="--every 4"`（4 コマに 1 枚だけ読む）。
  **秒数ではなくコマ番号で間引く** — スローモーションではコンテナの時刻が実時間と
  一致しないため、`fps=` で間引くとコマが複製されたり落ちたりする

### 解析そのものは検証済み

`make e2e` が、**既知の遅延を埋め込んだ動画を合成して解析にかけ、その値を言い当てるか**を
確認している（`e2e/latency-tool.spec.ts`）。カウンタは `?t=<ミリ秒>` で任意の時刻に静止できるので、
遅延 D・撮影レート R・コンテナ表示レート C の撮影を人手なしで再現できる。

- 50ms を埋め込んだ動画で中央値・最小・最大が 50ms になること、撮影レートも当てること
- **240fps で撮って 30fps の尺で書き出したスローモーション動画**でも、撮影レート 240fps を
  言い当て、遅延は 50ms のまま変わらないこと
- カウンタの周期をまたぐ区間でも正しく出ること

ここで確かめられないのはカメラ由来のもの（ブレ・ローリングシャッター・ピント・反射）だけ。
QR の生成、H.264 を経た劣化、複数 QR の検出、ホストの判定、周期のまたぎ、統計は全部通る。

## 4. 手順（自動が使えないとき）

QR が 1 コマも読めない場合は、数字とブロックを人が読む。

1. コマ送りして、**両方の数字が同時に読めるコマ**を探す
2. `遅延 = ホストの値 − ビューアの値`。負になったら `+ 10000`（数字は 10 秒で一巡する）
3. **離れた 10 コマ以上で読んで中央値を取る。** 1 コマの読みは撮影と表示のタイミングで
   ±1 フレームぶれる。1 回の読みを結果として採らない

数字が読めないコマでは、ブロックの点灯位置の差 × カウンタが表示している実測フレーム間隔で
粗く出せる。

| 日付 | 版 | ホスト | ビューア | 経路 | 送出解像度 | 中央値 | p10 / p90 | 標本 | 記録 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-08-11 | 0.1.0 (93ac7d5) | MacBook Air M1, 2020 / Built-in Retina Display 2880×1800 60Hz | iPad 10.2インチ 第9世代 MK2N3J/A | Wi-Fi | 2304×1440 | **67ms** | 50 / 116ms | 9481 / 14483 コマ（自動） | [json](latency/latency-20260811-93ac7d5.json) |
| 2026-08-11 | 0.1.0 (b204de9) | MacBook Air M1, 2020 / DeskPad Display 60Hz | iPad 10.2インチ 第9世代 MK2N3J/A | Wi-Fi | 不明 | 50ms | — | 約 10 コマ（手読み） | 下の行に置き換わった。参考 |

### 現状: 目標 60ms は未達（67ms）

**上の行が現時点の値。** 9481 コマの中央値なので、下の行（手読み約 10 コマの 50ms）より
はるかに信頼できる。**手読みの 50ms をもって「達成」とした判断は取り下げる。**
標本が 3 桁違い、しかも手読みは「読みやすいコマ」を人が選ぶぶん短い側に偏りやすい。

分布はきれいに表示フレームへ量子化されている。

| | 値 | 60Hz のフレーム数 |
| --- | --- | --- |
| p10 | 50ms | 3.0 |
| **中央値** | **67ms** | **4.0** |
| p90 | 116ms | 7.0 |

- **中央値 4 フレーム、良いときで 3 フレーム。** 目標 60ms は 3.6 フレームなので、
  **あと 1 フレーム削れば届く**という位置にいる。
- **p90 116ms の裾は Wi-Fi の揺らぎとみるのが自然。** 実時間 60 秒ぶんの録画なので、
  途中の停滞が入る。目標条件は有線 LAN（SPEC.md §1.3）である。
- **最大 500ms は `--max-latency` の上限そのもの。** 上限に張り付いた値は
  「実際はもっと大きかったが切られた」可能性がある。裾を見るなら上限を上げて測り直す。

### 解像度追従は意図どおり動いている

送出 2304×1440 は `VideoEncoding.followingSize` の計算とぴったり一致する。

```
ディスプレイ 2880×1800、iPad 10.2 の表示領域 2160×1620（物理ピクセル）
  縮尺 = min(2160/2880, 1620/1800) = 0.75
  必要な高さ = 1800 × 0.75 = 1350 → 直近上位の段階は 1440
  幅 = 2880 × 1440 / 1800 = 2304
```

**実機で SPEC.md §7.1 の裏が取れた。** ただし遅延の観点では**これが重い側に効いている疑いがある**。

### 仮説: 送出解像度が効いている（未確認）

2304×1440 は 3.32 Mpx で、**バジェット（SPEC.md §3.1）が前提にしている 1080p の 1.6 倍**。
過去の実測からエンコード時間を外挿すると:

| 送出解像度 | 画素数 | エンコード |
| --- | --- | --- |
| 1152×720 | 0.83 Mpx | 7.6ms（実測） |
| 1824×1140 | 2.08 Mpx | 9.9ms（実測） |
| 2880×1800 | 5.18 Mpx | 17.4ms（実測） |
| **2304×1440** | **3.32 Mpx** | **13ms 前後（外挿）** |

**これは外挿であって計測ではない。** 確かめるには同条件で内訳を取る（§7 の `make macos-serve`）。
もし本当に 13ms 前後なら、バジェットの 3–8ms を超えているぶんが 5ms ほど。それだけでは
67 → 50ms には届かないので、**内訳を見るまで「解像度を落とせば解決」と決めつけない。**

### 次にやること

1. **同条件で内訳を取る**（§7 の `make macos-serve`）。67ms の内訳が分からないままでは、
   どこを削ればよいかを決められない。**`make e2e` の内訳は条件が違うので使えない**
2. **有線 LAN で測り直す。** 目標条件はこれ。Wi-Fi の裾が消えれば中央値も下がる可能性がある
3. 裾を正しく見るため `ANALYZE_ARGS="--max-latency 2000"` でも一度かける

## 6. 読むときの注意

- **ホストのほうが必ず新しい。** ビューアが進んで見えたら、10 秒の巡回をまたいでいる
  （`+10000` する）か、2 画面を取り違えている
- **ビューア側の数字は縮小されて写る。** 解像度追従（SPEC.md §7.1）でビューアの表示サイズに
  合わせて送るため、720p まで落ちていることがある。読めなければビューアを大きい端末にするか、
  カメラを寄せる
- **1 コマだけで判断しない。** カメラの露光とディスプレイの走査は同期していないので、
  隣り合うコマで値が 1 フレームぶん前後する
- **内訳は同じ経路で取る。** `make e2e` の内訳（`apps/macos/build/selftest/latency.json`）は
  **内蔵ディスプレイ・Chrome・ループバック**のもので、実端末を Wi-Fi で撮った行の内訳には
  ならない。同条件で欲しいなら `make macos-serve` を使う（§7）

## 7. 送出解像度と内訳の取り違えに注意

**送出解像度は macOS の「ディスプレイ」設定でも DeskPad の設定でもない。** ホスト UI の
「◯◯ へ配信中」の右に出る値（`DisplayStream.activeConfiguration`）を読む。

解像度追従（SPEC.md §7.1）が出力するのは、次のどちらかだけ:

- **720 / 1080 / 1440 / 2160 のいずれかを高さとする値**（ディスプレイの縦横比を保つ）
- **ディスプレイの実解像度そのまま**（ビューアの表示領域がディスプレイ以上に広い場合。
  実解像度を超えて送っても意味がないため）

したがって、たとえば 3360×2100 のディスプレイなら送出は `2304×1440` や `1728×1080`、
あるいは `3360×2100` になる。**`1680×1050`（＝実解像度の半分、ポイント単位の値）は
この関数が返しえない。** この値が記録されていたら、ホスト UI ではなく macOS の
ディスプレイ設定を読んでいる可能性が高い。

**内訳を同条件で取りたい場合**は `make e2e` ではなく `make macos-serve` を使う。

```
make macos-serve SELFTEST_ARGS="--display 4 --duration 120"
```

`build/selftest/serve.json` の URL を実端末で開き、ホスト側で承認する。終了後の
`build/selftest/report.json` に、その端末・その経路での `encodeMs` / `frameWidth` /
`qualityLimitationReason` が入る。ビューア側（ジッタバッファ・デコード）は
ビューアの遅延オーバーレイ（`s` キーで表示）から読む。
