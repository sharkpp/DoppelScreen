# glass-to-glass 実測

SPEC.md §3.3 の実測手順と、その記録。**リリースごとに同条件で測って、この表に足す。**

内訳（エンコード・ジッタバッファ・デコード）は `make e2e` が自動で測る（docs/STACK.md §2.11）。
こちらは**表示までを含めた実際の遅延**。**人の手が要るのは撮影だけで、読み取りは自動**
（`make latency-analyze`）。

---

## 1. 何を測るか

ホスト画面が変化してから、ビューア端末の画面にそれが出るまで。**目標は 60ms 以下**
（有線 LAN、1080p60 — SPEC.md §1.3）。

`make latency-clock` が出すカウンタをホストの全画面に表示し、**ホストとビューアを 1 台の
カメラで同時に高速度撮影する。** 同じコマに写った 2 つのカウンタの差がそのまま遅延になる。

```
   ┌─ ホストの画面 ──┐   ┌─ ビューア端末 ──┐
   │  ▛▀▙ ▟▀▛ ▜▀▛    │   │  ▛▀▙ ▟▀▜ ▙▀▛    │   QR: 123456 と 123406 → 50ms
   │      4821       │   │      4772       │   数字: 4821 − 4772 = 49ms
   │  ▁▁▁█▁▁▁▁▁▁▁▁   │   │  ▁█▁▁▁▁▁▁▁▁▁▁   │   ブロック差 3 × 16.7 ≒ 50ms
   └─────────────────┘   └─────────────────┘
```

読み取り手段が 3 つ重なっている。**上から順に自動化に向く。**

| | 読む人 | 内容 |
| --- | --- | --- |
| **QR** | `make latency-analyze` | 経過ミリ秒（1000 秒周期）。位置も取れるので**どちらの画面かを指定する必要がない** — 時刻が新しい方が必ずホスト |
| **数字** | 人 | QR と同じ時刻の下 4 桁。QR が読めなかったときの逃げ道 |
| **ブロック** | 人 | 1 個 = 表示 1 フレーム。**桁がブレて読めないコマでも位置の差は残る** |

**基本は自動（§3）。** 人が数コマ読むのに対して、解析は数百コマの中央値を採る。
自動が使えないとき（QR が小さすぎる、ピントが来ていない等）だけ手で読む（§4）。

## 2. 準備

| | 内容 |
| --- | --- |
| ホスト | `make macos-run` で起動 → 「配信を開始」。**ディスプレイのリフレッシュレートを確認**（省電力で落ちていると測っても意味がない。カウンタ下段の実測値を見る） |
| ビューア | 画面ごとの URL を実端末で開き、ホスト側で**承認**する。ビューアは**フルスクリーン**にする（映像をタップ） |
| ネットワーク | 有線が基準。Wi-Fi でも測るなら別の行として記録する |
| 送出解像度 | ホスト UI の「◯◯ へ配信中」の右に出る実効値をそのまま記録する。解像度追従（SPEC.md §7.1）でビューア端末ごとに変わるので、**条件として必ず控える** |
| カメラ | **240fps** 推奨（iPhone のスローモーション。設定 → カメラ → スローモーション → 1080p/240fps）。60fps だと 1 コマ 16.7ms で、目標 60ms に対して分解能が足りない |

**カウンタは毎フレーム全体が描き替わる。** 静止画を映して測ると、静止時の送出停止（SPEC.md §4.3）が
効いて何も流れず、遅延ではなく「止まっていること」を測ることになる。

---

## 3. 手順（自動）

1. ホストで `make latency-clock` → 開いたページを**全画面**にする（ブラウザの全画面表示）
2. ホストの画面とビューア端末を**並べて置く**。カメラから見て**両方が正面**になるようにする
   （斜めから撮ると液晶の視野角で沈んで読めない）
3. 1 台のカメラで**両方が同時に画面内に入る**ように 240fps で 10 秒ほど撮る
4. 動画を Mac に取り込み、解析する

```
make latency-analyze VIDEO=~/Desktop/IMG_0001.MOV
```

```
動画: /Users/…/IMG_0001.MOV
  1920x1080 / 240.0fps / 9.8s
  2352 コマを解析します… 完了

遅延の中央値: 50ms   （目標 60ms 以下 — SPEC.md §1.3）
  最小 50ms / 最大 67ms / p10 50ms / p90 67ms
  読めたコマ 1866 / 2352 (79%)

分布（1 段 = 10ms）:
    50ms █████████████████████████ 1204
    60ms ███████████████ 662
```

各コマから QR を**すべて**読み、時刻の差を取って中央値を採る。**どちらの画面かを
指定する必要はない** — ホストは必ずビューアより新しいので、時刻の大小で決まる。

- **読めないコマが出るのは正常。** 表示の書き替えとカメラの露光は同期していないので、
  一部のコマは 2 枚のフレームをまたいだ QR になって復号できない。7 割読めれば十分。
  **0 コマなら QR が小さすぎるか、ピント・明るさの問題**（解析が候補を出す）
- 記録用の JSON も残せる: `ANALYZE_ARGS="--json docs/latency/latency-<日付>-<版>.json"`
- コマ数を間引きたいときは `ANALYZE_ARGS="--fps 120"`

### 解析そのものは検証済み

`make e2e` の「合成した録画から埋め込んだ遅延を言い当てる」が、**既知の遅延を埋め込んだ
動画を合成して解析にかけ、その値を言い当てるか**を確認している（`e2e/latency-tool.spec.ts`）。
カウンタは `?t=<ミリ秒>` で任意の時刻に静止できるので、遅延 D の撮影を人手なしで再現できる。

ここで確かめられないのはカメラ由来のもの（ブレ・ローリングシャッター・ピント・反射）だけ。
QR の生成、H.264 を経た劣化、複数 QR の検出、ホストの判定、周期のまたぎ、統計は全部通る。

## 4. 手順（自動が使えないとき）

QR が 1 コマも読めない場合は、数字とブロックを人が読む。

1. コマ送りして、**両方の数字が同時に読めるコマ**を探す
2. `遅延 = ホストの値 − ビューアの値`。負になったら `+ 10000`（数字は 10 秒で一巡する）
3. **離れた 10 コマ以上で読んで中央値を取る。** 1 コマの読みは撮影と表示のタイミングで
   ±1 フレームぶれる。1 回の読みを結果として採らない

数字が読めないコマでは、ブロックの点灯位置の差 × カウンタが表示している実測フレーム間隔で
粗く出せる。

## 5. 記録

同条件で比較できるよう、条件の列を必ず埋める。**空欄のある行は比較に使えない。**

| 日付 | 版 | ホスト | ビューア | 経路 | 送出解像度 | 中央値 | 最小 / 最大 | 内訳（`latency.json`） | 備考 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-08-11 | 0.1.0 (b204de9) | MacBook Air M1, 2020 / DeskPad Display 60Hz | iPad 10.2インチ 第9世代 MK2N3J/A | Wi-Fi | 1680×1050 ※要確認 | **50ms** | 50 / 67ms | [enc 7.6 / jb 15.4 / dec 3.2](latency/latency-20260811-b204de9.json) ※別条件 | **目標 60ms 以下を達成（M1 完了）** |

この行について:

- **Wi-Fi で 50ms。** 目標条件（有線 LAN — SPEC.md §1.3）より不利な経路で達成しているので、
  有線ならこれより良い。
- **最小 50ms と最大 67ms の差は 17ms = 60Hz の 1 フレームちょうど。** 読みが表示フレームに
  量子化されているということで、測定が素直に効いている裏付けになる（3 フレームぶんと 4 フレームぶん）。
- **内訳は別条件のもの。** リンク先は `make e2e`（内蔵ディスプレイ・Chrome・ループバック・1152×720）
  の値で、この行の経路（DeskPad Display・iPad・Wi-Fi）を分解したものではない。
  **この 50ms の内訳としては読めない**（§7）。
- 送出解像度 1680×1050 は**解像度追従が出力しうる値ではない**（§7）。要確認。

## 6. 読むときの注意

- **ホストのほうが必ず新しい。** ビューアが進んで見えたら、10 秒の巡回をまたいでいる
  （`+10000` する）か、2 画面を取り違えている
- **ビューア側の数字は縮小されて写る。** 解像度追従（SPEC.md §7.1）でビューアの表示サイズに
  合わせて送るため、720p まで落ちていることがある。読めなければビューアを大きい端末にするか、
  カメラを寄せる
- **1 コマだけで判断しない。** カメラの露光とディスプレイの走査は同期していないので、
  隣り合うコマで値が 1 フレームぶん前後する
- **測る前に `make e2e` を通しておく。** 内訳（`apps/macos/build/selftest/latency.json`）を
  同じ版で取っておくと、glass-to-glass が悪化したときにどの区間かを切り分けられる。
  ただし **`make e2e` は内蔵ディスプレイ・Chrome・ループバックで測る。** 実端末で測った行の
  内訳としてそのまま貼らない（§7）

## 7. 送出解像度と内訳の取り違えに注意

**送出解像度は macOS の「ディスプレイ」設定でも DeskPad の設定でもない。** ホスト UI の
「◯◯ へ配信中」の右に出る値（`DisplayStream.activeConfiguration`）を読む。

解像度追従（SPEC.md §7.1）が出力するのは、次のどちらかだけ:

- **720 / 1080 / 1440 / 2160 のいずれかを高さとする値**（ディスプレイの縦横比を保つ）
- **ディスプレイの実解像度そのまま**（ビューアの表示領域がディスプレイ以上に広い場合。
  実解像度を超えて送っても意味がないため）

したがって、たとえば 3360×2100 のディスプレイなら送出は `2304×1440` や `1728×1080`、
あるいは `3360×2100` になる。**`1680×1050`（＝実解像度の半分、ポイント単位の値）は
この関数が返しえない。** この値が記録されていたら、ホスト UI ではなく macOS の
ディスプレイ設定を読んでいる可能性が高い。

**内訳を同条件で取りたい場合**は `make e2e` ではなく `make macos-serve` を使う。

```
make macos-serve SELFTEST_ARGS="--display 4 --duration 120"
```

`build/selftest/serve.json` の URL を実端末で開き、ホスト側で承認する。終了後の
`build/selftest/report.json` に、その端末・その経路での `encodeMs` / `frameWidth` /
`qualityLimitationReason` が入る。ビューア側（ジッタバッファ・デコード）は
ビューアの遅延オーバーレイ（`s` キーで表示）から読む。
